BEAGLEPLAY SERVICE TROUBLESHOOTING / HANDOVER SUMMARY
==========================================================

Date: 10 August 2026

PURPOSE
-------
This document summarizes the current BeaglePlay service investigation. It is intended as a handover/troubleshooting reference before any new service, application, networking, GNSS, MCU, GPIO, Wi-Fi, modem, or system changes are made.

Remaining items to verify:

- failure/restart behavior
- whether another application can safely use the same serial device

14. SERVICE CLASSIFICATION REQUIRED
-----------------------------------
The final analysis should classify each service into one of these categories:

A. Service -> user's/developer application
    Example:
        gnss.service
           |
           +--> start_gnss.sh
                   |
                   +--> GNSS_Rover_Base.jar

B. Service -> developer script/program
    Example:
        service
           |
           +--> developer_script.sh
                   |
                   +--> developer executable

C. Service -> standard Linux executable
    Example:
        service
           |
           +--> /usr/bin/system-command

D. Service -> command embedded directly in unit
    Example:
        ExecStart=/bin/sh -c "..."

E. Service -> another system daemon/service

The user specifically wants to know which services fall into these groups.

23. USEFUL MANUAL COMMANDS
--------------------------
For a service:
    systemctl cat SERVICE.service
    systemctl status SERVICE.service --no-pager --full
    systemctl show SERVICE.service
    systemctl show SERVICE.service -p ExecStart -p ExecStartPre -p ExecStartPost
    systemctl list-dependencies SERVICE.service
    systemctl list-dependencies --reverse SERVICE.service
    journalctl -u SERVICE.service -b --no-pager

For a process:
    ps auxww | grep PROCESS_NAME
    pgrep -a PROCESS_NAME

For ports:
    ss -lntup

For open files/devices:
    lsof -p PID

For serial ownership:
    fuser -v /dev/ttyS*

For watchdog:
    ls -lah /dev/watchdog*
    fuser -v /dev/watchdog*

For GPIO:
    gpioinfo

For a program:
    ls -lah /path/program
    file /path/program
    readlink -f /path/program
    stat /path/program

For a shell script:
    cat /path/script.sh

25. TARGET ARCHITECTURE
-----------------------
The final objective is to reconstruct this type of chain for every custom service:

    SERVICE
       |
       +--> unit file
       |
       +--> ExecStart
              |
              +--> script/program/command
                     |
                     +--> child program/file
                            |
                            +--> hardware/network/files
                                   |
                                   +--> dependencies

The key question is not merely "what services are running?"

The key question is:

    "What is the actual execution and ownership architecture of the BeaglePlay?"

That means identifying:
- which service starts which program
- which script starts which child
- which program owns each device
- which program listens on each port
- which configuration files are used
- which files are read/written
- which services depend on one another
- what breaks when a service stops
- whether a new service can safely interact with an existing resource

27. HANDOVER PRINCIPLE
----------------------
Do not infer a service's actual behavior from its name.

Always follow:
    service -> ExecStart -> script/program -> child processes -> devices/ports/files -> dependencies

The user's Java/GNSS/UI software must be clearly distinguished from Linux/system services in the final documentation.
